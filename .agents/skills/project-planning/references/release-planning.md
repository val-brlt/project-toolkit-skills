# Release planning

The [shared versioning reference](../../project-scoping/references/versioning.md) and delivery schema are authoritative. This reference supplies planning procedure, not competing progress semantics.

1. Determine selected approved scope, verified existing release ledger/public contracts, actual code and deliverable outcomes. Preserve released versions and their evidence. Use `null` for unknown initial baseline; do not map `v1` or MVP to a number. Identify actual latest release through evidence, not a tag name alone. When planning ahead, distinguish a proposed predecessor from a delivered baseline; a baseline claim must be evidenced (or null). Do not invent dates/capacity.
2. Form incremental CHANGE slices; reuse existing IDs. Each maps to approved in-scope or supporting refs and has meaningful acceptance criteria and true prerequisites. Never assign future-only or unresolved items. Supporting work must enable approved scope; material new requirements return to their source approval.
3. Generate candidate release partitions in dependency order. Prefer independently useful/testable releases; validate all relevant dependencies, including feature prerequisites, and walk through critical user paths. Compare smaller versus larger releases only if material. Record trade-offs, unknowns, optional relative effort/risk, and approval in scratch. No estimates of tokens, dates or capacity without a basis.
4. Apply SemVer and the shared pre-1.0 policy. In a mixed release the most consequential change determines the bump. Before 1.0, compatible fixes are PATCH; new functionality or incompatible changes MINOR, with reset. At/after 1.0, incompatible public contracts MAJOR, compatible functionality MINOR, compatible fixes PATCH. Preserve published numbering; explicitly approve exceptional numbering and first release. Do not assign 1.0.0 without approved public contracts, stability criteria and approval. Treat `other` changes according to actual public impact; disclose unresolved classification. Never use an unchecked proposed baseline as delivery evidence.
5. Obtain explicit approval of assignments. Until then releases are `proposed`, assignments are not added to `planned_versions`. Once approved, release status is `planned` and reciprocal item planned_versions are updated. Neither planned nor published implies developed/delivered. Preserve any real historical progress. Unsliced approved features stay visible without invented tickets or version promises. MVP milestone remains independent of versions and first stability.
6. Mark each release's detail `deferred`, `detailed` or `historical`. Detail the nearest active release, plus any user-requested releases; a detailed release may have draft tickets until the package is approved and published. Historical applies only to evidenced developed/delivered releases; do not fabricate old tickets. If a later version is deferred, it is not executable. Each detailed change must be covered by one or more verifiable tickets; each ticket has one version and can span multiple changes. Validate blockers across version boundaries and require explicit reason for genuine dependencies. No forced parent issue per FEAT.
7. A replan of unshipped work, including already-published open tickets, can regroup changes and update exact existing issues and milestones after review; preserve stable identities, closed issues and delivered history. If a plan changes but scope and design do not, do not re-run scoping/UX/architecture. Keep revisions in ordinary canonical sections, not accumulating appendices. For bug fixes, use the [bounded PATCH path](patch-planning.md); breaking changes route to the affected design decisions.
